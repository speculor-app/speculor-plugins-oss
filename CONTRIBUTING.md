# Contributing — commit & PR conventions

All Speculor repos (`speculor-app`, `speculor-sdk`, `speculor-plugins`,
`speculor-plugins-oss`) follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).
Release changelogs are generated automatically from commit messages
(`feat`/`fix`/`perf` entries become the public release notes), so the format is
enforced by CI on every pull request.

## Commit message format

```
<type>(<scope>): <subject>

[optional body]

[optional footer(s)]
```

- **type** — one of the table below. Required.
- **scope** — optional, lowercase: a module, plugin, or area
  (`engine`, `gui`, `gpu`, `cli`, `video`, `sort_tracker`, `cmake`, ...).
  Multiple scopes may be comma-separated: `fix(record,replay): ...`.
- **subject** — imperative, concise, no trailing period. Say what the change
  does, not what you did ("add X", not "added X").
- **body** — free-form detail: the why, tradeoffs, gotchas. Wrap at ~72 chars.

| Type       | Use for                                             | In changelog        |
|------------|-----------------------------------------------------|---------------------|
| `feat`     | user-visible feature or capability                  | **Features**        |
| `fix`      | bug fix                                             | **Bug fixes**       |
| `perf`     | performance improvement                             | **Performance**     |
| `docs`     | documentation only                                  | no                  |
| `refactor` | code change that is neither a feature nor a fix     | no                  |
| `test`     | tests only                                          | no                  |
| `build`    | build system, packaging, dependencies               | no                  |
| `ci`       | CI workflows and runner config                      | no                  |
| `chore`    | maintenance that fits nothing above                 | no                  |
| `revert`   | reverts a previous commit                           | no                  |

Because `feat`/`fix`/`perf` subjects are published verbatim in release notes,
write them for a **user** reading the changelog, not for a teammate reading
`git log` — name the feature or the symptom, not the internal mechanics.

### Breaking changes

Append `!` after the type/scope and explain in a `BREAKING CHANGE:` footer.
Use for plugin-ABI, project-format (`.speculor`), or SDK-API breaks:

```
feat(sdk)!: widen timestamps to nanoseconds across the ABI

BREAKING CHANGE: plugins must rebuild against SDK >= 0.14; SpcPacket
timestamp fields are now int64 nanoseconds.
```

### Allowed non-conventional forms

- `Release X.Y.Z` — release version-bump commits (excluded from changelogs).
- `Revert "<original subject>"` — git-generated revert messages.
- Merge commits — generated by GitHub; never written by hand.

## Pull requests

- **PR titles follow the same convention** as commit subjects.
- PRs merge with **merge commits**; the changelog is built from the individual
  commits, so **every commit in the PR must conform** — CI checks all of them.
- Keep PR descriptions clean: what + why, no co-authored trailers.

## Releases & changelog

- Cutting a release: see `docs/claude/build-notes.md` in `speculor-app`
  (version bump in root `CMakeLists.txt`, `Release X.Y.Z` commit, annotated
  `vX.Y.Z` tag; the tag push builds and publishes).
- The release workflow generates the release notes with
  [git-cliff](https://git-cliff.org) (`cliff.toml` + `scripts/generate-changelog.sh`
  in `speculor-app`) across all four repos, and tags the sibling repos
  `speculor-vX.Y.Z` to record exactly which commits shipped.
